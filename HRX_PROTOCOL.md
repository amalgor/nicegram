# HRX Protocol — Hydra Route Exchange Open Protocol

**Version:** 0.1 draft
**Date:** 2026-04-03
**Status:** specification, pre-implementation

> Этот документ описывает forward-looking protocol-only направление. Текущая shipping surface репозитория на 2026-04-04 — embedded-wallet Hydra mobile app с Balance/Payments/Providers hub, documented in `SERVICE_MANUAL.md`.

## Overview

HRX Protocol decouples the **route marketplace** from the **VPN client**. Hydra App is a marketplace + AI agent + wallet. VPN functionality stays in existing clients (v2rayNG, Shadowrocket, Clash, sing-box, etc.). This eliminates the requirement for VpnService/NEVPNManager permissions and the associated Organization developer account requirement on both Google Play and Apple App Store.

```
+---------------------+     +----------------------------+     +--------------------+
|  VPN Client          |     |  Hydra App                  |     |  Crypto Wallet      |
|  (v2rayNG, Clash,    |     |  (marketplace + AI + credit) |     |  (MetaMask, etc.)   |
|   Shadowrocket...)   |     |                              |     |                     |
+----------+----------+     +-------------+----------------+     +---------+----------+
           |                               |                               |
           |  HRX Subscribe                |  HRX Provider                 |  HRX Pay
           |  (GET subscription URL)       |  (register/manage offers)     |  (WalletConnect/
           |                               |                               |   deep link)
           +----------v-------------------v-------------------------------v-+
                      |         api.hydra-net.work (Cloudflare Worker)       |
                      +--+--------+--------+---------+--------+-------------+
                         |        |        |         |        |
                    RouteBook  DealBoard  ERC-8004   USDC   KV Cache
                    (Base)     (Base)     (Base)    (Base)  (Cloudflare)
```

## Motivation

### App Store constraints

| Platform | VPN apps | Crypto wallet apps | Marketplace-only app |
|----------|----------|--------------------|----------------------|
| Apple App Store | Organization only (Guideline 5.4) | Organization only (Guideline 3.1.5) | Individual OK |
| Google Play | Organization only (VpnService policy) | Organization only | Individual OK |

By positioning Hydra App as a marketplace that generates subscription URLs for external VPN clients and uses WalletConnect for external crypto wallets, neither VpnService nor embedded wallet is needed. Individual developer accounts suffice for both stores.

### Ecosystem leverage

Users already have VPN clients installed. Providers already run VLESS/Reality/Shadowsocks servers. HRX Protocol connects supply and demand without requiring either side to switch tools.

## 1. HRX Subscribe

The core protocol. Serves personalized proxy configurations in formats compatible with the v2ray/clash/sing-box ecosystem.

### Endpoints

```
GET https://api.hydra-net.work/sub/{token}
GET https://api.hydra-net.work/sub/{token}?format=v2ray      # default
GET https://api.hydra-net.work/sub/{token}?format=clash
GET https://api.hydra-net.work/sub/{token}?format=singbox
GET https://api.hydra-net.work/sub/{token}?format=json        # machine API
```

### Token

Personal, generated by Hydra App on registration. Bound to device_id / credit account. Stored in Cloudflare KV:

```
Key:   sub_token:{token}
Value: {
  "device_id": "...",
  "credit_tier": "trial|basic|linked",
  "region_hint": "RU",
  "preferences": { "prefer_free": true },
  "created_at": 1735600000
}
```

### Response: format=v2ray (default)

```http
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Subscription-Userinfo: upload=0; download=1073741824; total=5368709120; expire=1735689600
Profile-Update-Interval: 6
Profile-Title: base64(HRX Routes)
```

Body is base64-encoded list of proxy URIs, one per line before encoding:

```
vless://uuid@server1.example.com:443?security=reality&type=tcp&sni=www.google.com&fp=chrome&pbk=xxx&sid=01#HRX-US-Premium-42
vless://uuid@server2.example.com:443?security=reality&type=tcp&sni=www.microsoft.com&fp=chrome&pbk=yyy&sid=02#HRX-DE-Free-17
ss://method:password@server3.example.com:8388#HRX-NL-Free-9
```

`Subscription-Userinfo` header is a de-facto standard recognized by v2rayNG, Shadowrocket, and others. Maps to:
- `download` = credit used bytes
- `total` = credit limit bytes
- `expire` = credit expiry unix timestamp (0 = no expiry)

`Profile-Update-Interval` = recommended refresh interval in hours.

### Response: format=clash

```yaml
proxies:
  - name: "HRX-US-Premium-42"
    type: vless
    server: server1.example.com
    port: 443
    uuid: "..."
    tls: true
    reality-opts:
      public-key: "xxx"
      short-id: "01"
    client-fingerprint: chrome
    servername: www.google.com

  - name: "HRX-DE-Free-17"
    type: vless
    server: server2.example.com
    port: 443
    uuid: "..."
    tls: true
    reality-opts:
      public-key: "yyy"
      short-id: "02"
    client-fingerprint: chrome
    servername: www.microsoft.com

proxy-groups:
  - name: "HRX Auto"
    type: url-test
    proxies:
      - "HRX-US-Premium-42"
      - "HRX-DE-Free-17"
    url: "http://www.gstatic.com/generate_204"
    interval: 300

  - name: "HRX Select"
    type: select
    proxies:
      - "HRX Auto"
      - "HRX-US-Premium-42"
      - "HRX-DE-Free-17"
      - "DIRECT"

  - MATCH,HRX Auto
```

    {

```json
{
  "version": 1,
  "updated_at": 1735600000,
  "ttl_seconds": 300,
  "credit": {
    "used_bytes": 1073741824,
    "limit_bytes": 5368709120,

    "debt_micro_usdc": 0

    {
      "id": "hrx-42",

```

### Route naming convention

```
HRX-{REGION}-{Free|Premium}-{offer_id}
```

VPN clients sort by name, so users see routes grouped by region and tier.

### Route selection logic (server-side, in Worker)

1. Read RouteBook offers from KV cache (periodic Cron Trigger refresh from on-chain)
2. Merge gossip-sourced unstaked routes (relayed via `/provider/heartbeat`)
3. Filter by user's `region_hint`
4. Apply credit tier filter:
   - `trial` → free routes only (price = 0)
   - `basic` → free + cheap premium (price <= threshold)
   - `linked` → all routes
5. Apply pre-computed AI scoring (stored in KV) for ordering
6. Decode `endpoint_ciphertext` from RouteBook into proxy URIs
7. Format according to requested output format
8. Attach `Subscription-Userinfo` header from KV quota data

## 2. HRX Provider

REST/WSS API for route providers (owners of VLESS/SS/WSS servers).

### Base URL

```
https://api.hydra-net.work/provider
```

### Register

```http
POST /provider/register
Authorization: Bearer {provider_api_key}
Content-Type: application/json

{
  "agent_id": 3377,
  "endpoint_url": "vless://uuid@myserver.com:443?security=reality&type=tcp&sni=www.google.com&fp=chrome&pbk=xxx&sid=01",
  "protocols": ["vless"],
  "region": "US",
  "price_per_gb_usdc": "1.00",
  "bandwidth_mbps": 100,
  "stake_mode": "deferred"
}
```

Response:
```json
{
  "provider_id": "prov_abc123",
  "offer_id": null,
  "status": "gossip_only",
  "subscribe_endpoint": "wss://relay.hydra-net.work?agent=3377",
  "message": "Announced via gossip. Stake 1 USDC to register on-chain for higher visibility."
}
```

`stake_mode` values:
- `"deferred"` — start with gossip announcements; after earning enough, auto-graduate to RouteBook on-chain
- `"immediate"` — `createOffer` on-chain immediately (requires USDC balance for stake)
- `"relay_backed"` — provider behind NAT, uses Durable Object relay session at `wss://relay.hydra-net.work?agent={agent_id}`

### Heartbeat

```http
POST /provider/heartbeat
Authorization: Bearer {provider_api_key}
Content-Type: application/json

{
  "provider_id": "prov_abc123",
  "active_connections": 5,
  "bandwidth_used_gb": 2.3,
  "uptime_seconds": 86400
}
```

Worker updates liveness in KV. Routes without heartbeat for >5 min are marked stale and penalized in scoring.

### Earnings

```http
GET /provider/earnings?provider_id=prov_abc123
```

Response:
```json
{
  "total_usdc": "12.50",
  "pending_usdc": "1.20",
  "sessions_completed": 47,
  "bytes_relayed_gb": 23.7,
  "reputation_score": "4.2"
}
```

### Panel import (future)

Compatibility with existing VPN management panels (X-UI, 3X-UI, Marzban):

```http
POST /provider/bulk-import
Content-Type: application/json

{
  "panel_type": "3x-ui",
  "panel_url": "https://my-panel.com:2053",
  "api_key": "...",
  "auto_sync": true,
  "region": "US",
  "price_per_gb_usdc": "0.50"
}
```

Worker polls the panel API periodically and creates/updates offers accordingly.

## 3. HRX Pay

Three payment tiers, from zero-friction to crypto-native.

### Level 0: Free tier (no payment)

- Trial credit (configurable, default 5 GB) assigned on subscribe token creation
- Only free routes (price = 0) are served
- `Subscription-Userinfo` header shows remaining trial balance

### Level 1: In-app credit top-up (via Hydra App)

Hydra App shows balance and "Top up" button. Three methods:

| Method | Flow | Availability |
|--------|------|-------------|
| P2P Deal | DealBoard escrow: local bank transfer to dealer → USDC release | Everywhere |
| Fiat on-ramp | MoonPay / Coinbase OnRamp widget | Geo-restricted |
| Direct USDC | QR code / deep link to send USDC to user's credit address | Crypto-native users |

Credit top-up updates the KV record for the user's subscribe token, immediately affecting which routes are served.

### Level 2: WalletConnect (external wallet)

```http
POST /pay/session
Content-Type: application/json

{ "token": "{subscribe_token}", "amount_usdc": "5.00" }
```

Response:
```json
{
  "wc_uri": "wc:abc123@2?relay-protocol=irn&symKey=...",
  "payment_address": "0x...",
  "amount_wei": "5000000",
  "chain_id": 84532,
  "expires_at": 1735600600
}
```

Hydra App or a web page displays QR / deep link for MetaMask / Trust Wallet.

### Level 3: x402 micropayment (future, machine-to-machine)

```http
GET /sub/{token}
→ 402 Payment Required
   X-Payment: x402/1.0
   X-Payment-Amount: 100
   X-Payment-Asset: USDC
   X-Payment-Network: base-sepolia
   X-Payment-Receiver: 0x...
```

VPN clients with built-in x402 SDK can pay per subscription refresh. Future protocol extension.

### Credit-to-usage tracking

Worker logs bytes transferred per device_id via KV (existing `checkAndUpdateQuota` in `hydra-relay-worker`). The `format=json` response and `Subscription-Userinfo` header return current usage.

## 4. HRX Discovery

Public JSON API for programmatic access to the exchange. Does NOT expose endpoint URIs (those require a valid subscribe token).

### Endpoints

```
GET /api/v1/offers
GET /api/v1/offers?region=US&protocol=vless&max_price=2.0
GET /api/v1/offers/{offer_id}
GET /api/v1/deals?currency=RUB
GET /api/v1/deals/{offer_id}
GET /api/v1/agent/{agent_id}/reputation
GET /api/v1/stats
```

### Example: GET /api/v1/offers

```json
{
  "total": 42,
  "offers": [
    {
      "offer_id": 1,
      "agent_id": 3377,
      "region": "US",
      "protocols": ["vless"],
      "price_per_gb_usdc": "1.00",
      "bandwidth_mbps": 100,
      "stake_usdc": "1.00",
      "reputation": { "score": "4.2", "feedback_count": 15 },
      "active": true,
      "created_at": 1735600000
    }
  ]
}
```

Endpoint URIs are intentionally omitted from Discovery responses. This prevents scraping and ensures payment/credit is required to use routes.

### Example: GET /api/v1/stats

```json
{
  "total_offers": 42,
  "active_offers": 38,
  "total_providers": 15,
  "total_subscribers": 1200,
  "regions": ["US", "DE", "NL", "JP", "SG"],
  "protocols": ["vless", "shadowsocks"],

}
```

## 5. Security

| Threat | Mitigation |
|--------|-----------|
| Token leaking | Rate limit per token (max 10 req/min), optional IP binding |
| Endpoint scraping | Endpoints only via Subscribe with valid token; Discovery API omits URIs |
| Provider impersonation | ERC-8004 agent identity + USDC stake on RouteBook |
| DDoS on Subscribe | Cloudflare WAF + rate limiting (built-in) |
| Credit abuse | Device fingerprint + KV quota tracking (existing) |
| Token sharing | Usage metering — shared tokens exhaust quota quickly |
| Man-in-the-middle | All endpoints TLS-only; VLESS/Reality provide additional encryption layer |
| Rogue provider (honeypot) | Reputation scoring, stake slashing, multi-hop (future) |

## 6. Implementation mapping

| Component | Where | Dependencies |
|-----------|-------|-------------|
| Subscribe endpoint | New routes in `hydra-relay-worker` or separate `hydra-subscribe-worker` | RouteBook RPC (cached in KV), credit KV |
| v2ray/clash/singbox formatters | TypeScript in Worker | Parsing `endpoint_ciphertext` fields |
| Provider API | Routes in `hydra-relay-worker` | RouteBook write (provider's own wallet), KV heartbeat |
| Pay session | Route in Worker + WalletConnect relay | DealBoard, USDC contract |
| Discovery API | Routes in Worker (read-only) | RouteBook read, Reputation read |
| Token generation | Hydra App → Worker API | KV token store |
| RouteBook cache | Worker Cron Trigger (every 60s) | Base Sepolia RPC (`alloy` or `ethers` via fetch) |

### Existing infrastructure reuse

| Existing component | HRX Protocol role |
|--------------------|-------------------|
| `hydra-relay-worker/src/index.ts` | Host for Subscribe, Provider, Pay, Discovery routes |
| `HYDRA_QUOTAS` KV namespace | Credit/usage tracking per device_id |
| `HydraProviderSession` Durable Object | Relay-backed provider sessions |
| `HydraRouteBook` contract (Base Sepolia) | On-chain offer storage |
| `HydraDealBoard` contract (Base Sepolia) | P2P fiat-to-USDC escrow |
| ERC-8004 Identity/Reputation registries | Agent identity and trust scoring |
| `RouteDiscoveryService` (Rust) | Reference implementation for route selection logic |
| `endpoint_ciphertext` field convention | Already stores `vless://` and `wss://` URIs |

### Endpoint ciphertext to proxy URI conversion

`RouteOfferView.endpoint_ciphertext` already stores raw proxy URIs (`vless://...` or `wss://...`). For the Subscribe protocol:
1. Filter by protocol (vless → v2ray/clash/singbox format; wss → Hydra relay format)
2. Append `#HRX-{region}-{tier}-{offer_id}` fragment for naming
3. Base64-encode the full list for v2ray format
4. Map fields to YAML/JSON structures for clash/singbox formats

## 7. Phased implementation plan

### Phase A — MVP (target: ~150 LOC TypeScript)

Add to existing `hydra-relay-worker`:
- Route handler: `GET /sub/{token}` → v2ray base64 format
- `fetchRouteBookOffers()` with KV cache (key: `routebook_cache`, TTL: 60s)
- `formatV2raySubscription(offers, credit)` function
- `Subscription-Userinfo` header from KV quota
- Token = device_id for now (no separate generation step)
- Cron Trigger for periodic RouteBook refresh

### Phase B — Multi-format + Provider API

- Clash YAML and sing-box JSON formatters
- `/provider/register` + `/provider/heartbeat` routes
- Panel import endpoint for 3X-UI / Marzban
- Token generation via Hydra App → `POST /sub/create-token`
- Region-based filtering

### Phase C — Pay integration + Discovery

- WalletConnect session for credit top-up (`POST /pay/session`)
- `/api/v1/offers` public Discovery API
- x402 payment header support (402 response)
- Credit tier → route filtering logic
- AI-scored route ordering (pre-computed, stored in KV)

### Phase D — Ecosystem growth

- SDK packages: `hrx-client-js`, `hrx-client-py`
- Provider SDK for panel integration
- WebSocket push notifications for route updates
- Multi-chain support (Base mainnet, Arbitrum)
